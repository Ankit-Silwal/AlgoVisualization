# Running and deploying

## Local services

`docker compose up -d postgres` binds PostgreSQL to **127.0.0.1:5437**, using the named volume `algo_data`. The Compose password is intentionally a local-development default. Use your own database credentials in other environments. `docker compose down` preserves data; do not use `down -v` unless you intend to delete it.

`npm run runner:build` creates `algovisual-runner:local` with Node 22, Python 3, Java 17, and GCC/C17. The image downloads toolchains once. Each test creates a fresh container without host mounts, credentials, or a Docker socket. Set `RUNNER_ENABLED=true` only after building the image, then restart Next.js.

## Execution boundaries

Each job has no network, a read-only root, non-root UID/GID 65534, all Linux capabilities dropped, no-new-privileges, one CPU, 384 MiB RAM (no extra swap), a 64-process ceiling, a 64 MiB work tmpfs, a 16 MiB temporary tmpfs, a 1 MiB file-size limit, and bounded returned output. The app removes timed-out containers. User source reaches the runner over stdin; no user-controlled shell command is executed on the host.

Compilation runs inside the same restricted container. Java uses a 96 MiB heap and serial GC; Node uses a 96 MiB heap. Python and C use the container memory limit. Actual language versions are determined by the runner image, not the local machine.

Docker containers share the host kernel and are not a sufficient sole boundary for a hostile public multi-tenant judge. The current app also has a shared experiment list, no sign-in, no per-user ownership, and an in-process concurrency limit (not distributed rate limiting).

## Public production requirements

Before exposing code execution publicly, add authentication and authorization, quotas/rate limits, per-user experiment ownership, a persistent job queue, dedicated runner hosts, stronger isolation such as microVMs or gVisor, monitoring, and image patching. Do not mount the Docker socket into a general public web container. Keep `RUNNER_ENABLED=false` on an ordinary frontend/serverless deployment. The modeling workspace can operate with execution disabled.

Next.js production build: `npm ci && npm run db:migrate && npm run build`, then `npm start`. Ensure `DATABASE_URL` is set on both migration and runtime processes. Prisma Client is generated by `postinstall`. For a managed PostgreSQL service, follow its required TLS connection parameters. Host this server on a trusted local interface until access control is added.

## Troubleshooting

- **Prisma engine download fails:** allow npm/Prisma download access and run `npm run db:generate`.
- **Database unavailable:** verify `DATABASE_URL`, `docker compose ps`, and `npm run db:migrate`.
- **Runner unavailable:** verify Docker is running Linux containers, build the image, set the env flag, restart the app.
- **Java compile errors:** use class `Main`; library examples are complete programs. LeetCode `Solution` methods require a wrapper.
- **Search gets “Wrong answer”:** default expectations are sorted arrays. Use the expected search index and provide sorted input for binary search.
- **Unexpected timings:** process/JVM startup dominates tiny cases. Use repeated, larger representative inputs; do not interpret one short sample as an asymptotic proof.
- **Unexpected graph complexity:** custom-code inference is intentionally conservative. Review the case models and factors in the editor.
